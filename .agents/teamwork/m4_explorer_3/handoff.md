## 2. Logic Chain

1. **Identification of Gate Risk**:
   In Milestone 3 Iteration 1, the gate failed specifically because reviewers and challengers rejected "Self-certifying facade tests in `f13`, `b13`, and `b14` using local closures instead of importing genuine services" (see `orchestrator_1/GATE_STATUS.md` line 65).
   Milestone 4 currently has the exact same facade pattern in `f16`, `f17`, `b16`, and `b17`. If not replaced with genuine imports of `CloudMigrationService` and `ParityVerificationService`, M4 will fail the gate immediately.
2. **Dependency Injection Requirement for Headless Execution**:
   To test `CloudMigrationService` and `ParityVerificationService` inside headless Node under `npx tsx --test` in < 500 ms without requiring a live Firestore backend or running Electron window:
   - The services must support **injectable providers** (`ILocalDatabaseExtractor`, `IBackupProvider`, `ICloudVaultUploader`, `IMigrationProgressSink`).
   - In production Electron, the services use default implementations wired to `DatabaseManager`, `BackupManager`, Firestore REST, and `window.dispatchEvent`.
   - In test runners, tests inject in-memory or spy implementations that execute instantly while exercising 100% of the genuine pipeline logic, state transitions, payload packaging, encryption, batching, error rollback, and telemetry.
3. **Fault Tolerance & Atomic Rollback Mechanism**:
   - *Phase 1 (Pre-flight)*: Failure (e.g. `ENOSPC`, read-only disk, missing store DB) throws a typed `PreflightError` and terminates the pipeline before any extraction or cloud upload begins. Cloud mutation count is strictly 0.
   - *Phase 2-4 (Extract, Package, Encrypt)*: Failures (corrupted tables, encryption errors) abort immediately. No cloud requests are sent.
   - *Phase 5 (Batch Upload)*: Transient failures (HTTP 500, socket timeout) trigger retry with exponential backoff (up to 3 retries). If retries exhaust:
     - Pipeline aborts with status `'failed'`.
     - Rollback verification: Local SQLite database was opened read-only; its file SHA-256 and records are 100% identical to pre-migration state.
     - Pre-flight backup file is preserved on disk with path recorded in the failure receipt.
     - Cloud documents use deterministic IDs (`${storeId}_${vaultType}_${docId}`). A subsequent re-run idempotently overwrites existing documents without creating duplicates.
4. **Parity Verification Logic**:
   - `ParityVerificationService` computes canonical SHA-256 hashes for each record (RFC 8785) and aggregates them into sorted table digests (Merkle roots).
   - Bi-directional comparison checks both directions: local vs cloud and cloud vs local.
   - It flags: row count mismatches, missing rows, extra rows, tampered values, float precision drift, array order drift, and schema differences.
   - When verified 100%, it generates a cryptographically signed HMAC-SHA256 certificate.
5. **Real-time Telemetry Contract**:
   - Emits `sbx:migration-progress` with `{ phase, percent, currentTable, recordsMigrated, totalRecords }`.
   - Emits `sbx:migration-completed` on success and `sbx:migration-failed` on error.

1. **Read-Only Explorer Scope**:
   In accordance with explorer guidelines, no source files were modified. The test blueprints and service interfaces documented below are ready for implementation by the M4 worker agent.
2. **PBKDF2 Iteration Speed**:
   PBKDF2-HMAC-SHA256 with 600,000 iterations takes ~70ms on modern hardware for the initial key derivation. Because `StoreKeyCache` caches the key for 1 hour, subsequent test runs complete in < 1ms. For test suites running in headless Node, tests can utilize the cached key or supply an explicit test passphrase.

   In production Electron renderer, Firestore batch uploads can use either Firebase Web SDK or direct REST API (`batchWrite`). The designed `ICloudVaultUploader` interface abstracts this completely.

  // 1. Canonical JSON Key-Order Independence
  await t.test('test_f17_canonical_json_sorting_guarantees_key_independence', () => {
    const objA = { z: 1, a: 2, m: { y: 10, b: 20 } };
